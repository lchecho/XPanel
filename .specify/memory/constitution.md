# XPanel Constitution

## Core Principles

### I. SQLite 是唯一权威状态

SQLite MUST 是用户、凭证、节点、入站、端口分配、用户节点分配、配额周期、累计流量和
生命周期状态的唯一权威数据源。Xray 中的入站、用户列表和统计计数器 MUST 视为可丢失、
可重建的运行时投影，不得成为业务事实的唯一存储位置。

- 管理型用户 MUST 先持久化期望状态，再由同步流程投影到 Xray。
- Xray 启动、重启或重新连接后，协调器 MUST 从 SQLite 恢复所有应监听的面板入站和
  应启用的用户，并确保已禁用、已过期或配额超限的用户不会被重新加入，其入站不被重建。
- 业务代码不得依赖手工修改的 Xray 用户配置。面板管理的入站与用户 MUST 处于面板保留
  命名空间内且归属明确；命名空间之外的入站、路由和传输配置由运维管理，面板 MUST 只读，
  不得与其产生标识或端口冲突。
- 任何展示给用户的流量、配额和状态 MUST 来源于已持久化的数据，而不是一次性的
  Xray API 查询结果。

理由：Xray 的动态用户和统计数据可能在进程重启时变化，只有持久化的期望状态才能
保证系统可以自动恢复和对账。

### II. Xray 集成必须隔离且版本化

所有 Xray 操作 MUST 通过单一的 Xray Adapter 边界完成。业务模块不得直接依赖
Xray protobuf 类型、编辑 Xray 用户配置文件，或为普通用户创建、修改、禁用操作
重启 Xray。

- 动态用户与入站生命周期操作 MUST 使用 HandlerService；流量读取 MUST 使用 StatsService。
- 面板 MAY 通过 HandlerService 创建和移除入站，但 MUST 限定在面板保留命名空间内；
  命名空间之外的入站 MUST 保持只读，不得被面板修改或移除。
- 面板创建的入站 MUST 在 SQLite 中持有权威的端口分配与期望状态。端口唯一性 MUST 由面板
  自身的约束保证，MUST NOT 依赖 Xray 拒绝重复端口。
- 面板 MUST NOT 创建或保留没有受管客户端的入站；停止某个用户的访问 MUST 通过移除整条
  入站实现，以免入站退化为服务端密钥可直接连接的形态。
- 入站创建或移除失败 MUST 视为可能已部分生效：MUST 先读后写确认实际状态，必要时补偿
  移除残留入站，再按有界退避重试。
- 面板 MUST NOT 通过写入或编辑 Xray 配置文件来持久化入站；重启后的恢复 MUST 由协调器
  从 SQLite 重建。
- Xray release、protobuf 定义和 Go 依赖版本 MUST 固定。升级 MUST 经过入站增删、用户增删、
  统计读取、重启恢复和兼容性测试后才能合并。
- Adapter MUST 将 Xray 错误转换为项目内部的稳定错误类型，并为每个调用设置超时。
- 同一节点的变更操作 MUST 串行或使用明确的低并发上限；失败操作 MUST 使用有界
  指数退避重试，不得形成无上限请求风暴。
- 新协议接入 MUST 作为独立适配能力实现，并明确其动态用户管理和统计能力；不得
  假设所有 Xray 入站协议具有相同的 UserManager 行为。

理由：隔离协议细节可以控制上游版本变化的影响，并让业务规则能够独立测试。入站生命周期
交给面板可以实现按用户隔离的端口，但 Xray 不校验重复端口且创建失败后可能残留已注册入站，
因此授权必须与命名空间、端口唯一性和补偿语义的约束一并写入，否则会把控制面变成故障源。

### III. 流量核算准确且配额语义诚实

每个用户节点分配 MUST 使用不可变且全局唯一的统计标识；显示名称和真实邮箱不得
充当持久身份键。流量核算 MUST 使用 Xray 上下行字节计数器的增量，并在同一事务中
更新采集游标、累计流量以及日和配额周期聚合。

- 默认采集周期 MUST 为 5 秒，并可按节点配置。若配置超过 60 秒，功能规格 MUST
  明确记录可接受的超额风险及理由。
- 常规运行只保存当前累计值、日聚合、配额周期聚合和采集游标；不得默认永久保存
  每次轮询产生的原始采样记录。
- 采集器 MUST 识别 Xray 重启、计数器下降或统计纪元变化，禁止把负增量计入用量。
- 达到配额时，系统 MUST 先持久化 `quota_exceeded` 期望状态，再立即请求从 Xray
  移除该用户，并持续重试直至实际状态收敛。
- 新配额周期开始时，系统 MUST 结算旧周期、建立新基线、将新周期用量归零，然后
  重新加入符合启用条件的用户。
- 产品文案和 API MUST 明确：该机制是轮询式配额控制，主要阻止新连接，允许存在
  采集延迟、RPC 延迟以及已有连接造成的少量超额；不得宣称逐字节硬限额或实时限速。

理由：高频采集与低粒度持久化可以同时获得秒级响应和可控的数据增长，而明确限制
可以避免将控制面能力误认为数据面硬限流。

### IV. 状态变更必须幂等、可恢复

创建、修改、禁用、配额封禁、周期恢复和删除 MUST 建模为显式状态转换。跨 SQLite
和 Xray 的操作不得假装是分布式事务；系统 MUST 采用持久期望状态、可重试操作和
周期性协调来实现最终一致。

- 生命周期至少 MUST 区分 `active`、`enabling`、`disabling`、`quota_exceeded`、
  `disabled` 和 `deleted`，或提供语义等价且有文档说明的状态。
- 每个外部变更 MUST 具有稳定操作标识或等价的幂等键；重复执行不得创建重复用户、
  重复扣减流量或错误恢复已禁用用户。
- 数据库状态与待执行动作 MUST 在一个 SQLite 事务中提交。RPC 成功确认、失败原因和
  下一次重试时间 MUST 可追踪。
- 协调器 MUST 在进程启动、节点重连和固定周期运行，并修复期望状态与 Xray 实际
  状态之间的差异。
- 修改凭证若需要“先删除、后添加”，MUST 定义中途失败时的补偿或重试行为。
- 配额周期边界 MUST 使用显式时区；内部时间戳 MUST 使用 UTC，面向用户的周期时区
  MUST 持久化，禁止依赖服务器本地时区的隐式行为。

理由：控制面与 Xray 之间无法共享原子事务，只有显式状态机和协调机制才能安全处理
崩溃、超时和重复请求。

### V. 安全和可观测性默认开启

Xray 管理接口、用户凭证和管理操作 MUST 按敏感控制面资产处理。系统 MUST 提供足以
定位节点、用户分配和操作结果的结构化审计信息，同时禁止泄露凭证。

- 单机部署时，Xray gRPC API MUST 仅监听回环地址或等价的本机安全通道，不得直接
  暴露到公网。
- 远程节点管理 MUST 通过受认证的 Agent 通道完成，并使用双向 TLS 或等价的强身份
  验证和传输加密。
- SQLite 文件、备份和包含凭证的配置 MUST 使用最小文件权限；日志、指标和错误响应
  MUST 对 UUID、密码、密钥和令牌进行脱敏。
- 管理端点 MUST 要求身份认证和授权；创建、修改、禁用、恢复、删除和配额变更 MUST
  写入审计日志。
- 浏览器管理端 MUST 使用服务端管理的认证会话。生产环境 Cookie MUST 设置 Secure、
  HttpOnly 和合适的 SameSite 属性，并具备明确的过期和撤销机制。
- 所有改变状态的浏览器请求 MUST 使用非 GET 方法并验证 CSRF 令牌；认证失败、权限
  不足和 CSRF 失败 MUST 使用一致且不泄露敏感信息的响应。
- 结构化日志 MUST 至少包含节点标识、用户节点分配标识、操作标识、目标状态、结果和
  延迟。流量采集失败、协调失败和持续不同步 MUST 可被监测。
- API 输入 MUST 校验，密钥比较 MUST 使用安全实现，敏感值不得出现在 URL 查询参数。

理由：管理面板能够直接授予代理访问权，默认安全和可追踪性是正确性的一部分，而非
上线后的附加工作。

### VI. 服务端渲染与渐进增强优先

第一阶段管理界面 MUST 由 Go 使用 `html/template` 服务端渲染，并与后端作为同一
应用交付。HTMX 或原生 JavaScript MAY 用于局部刷新和交互增强，但用户、节点、配额
和访问控制等核心操作不得依赖独立 SPA 运行时才能完成。

- 模板和 HTTP Handler MUST 只承担传输与表现职责。Handler MUST 调用 application
  service，不得直接访问 SQLite 或 Xray Adapter。
- 完整页面和 HTML fragment MUST 复用相同的业务用例、授权规则和输入校验；不得在
  模板或浏览器脚本中复制配额与状态转换规则。
- 生产构建 MUST 使用 `go:embed` 或等价方式包含模板和静态资源，形成单个可部署的
  应用制品。运行时不得依赖 Node.js 或公共 CDN。
- 页面 MAY 以与流量采集周期一致的频率轮询局部状态。初始版本不得引入 WebSocket，
  除非功能规格证明单向轮询或 SSE 无法满足需求。
- 稳定的外部集成和远程 Agent 接口 MUST 使用版本化 JSON 或 gRPC 契约；管理页面
  无需为了形式上的前后端分离而为每个视图建立重复 JSON API。
- 引入独立 React、Vue 或其他 SPA、独立前端部署流水线或生产 Node.js 运行时，MUST
  先有功能规格说明交互复杂度、独立发布需求、迁移成本和运维收益。
- 关键管理流程 MUST 支持键盘操作、可识别的错误反馈和服务端校验；渐进增强失败时
  不得造成静默的状态变更或不可恢复的数据丢失。

理由：当前产品以少量用户的管理表格、表单和流量视图为主，服务端渲染可以减少认证、
跨域、构建和部署复杂度，同时保留未来通过稳定业务边界迁移前端的能力。

## 技术与运行约束

- 第一阶段后端 MUST 使用 Go，并采用模块化单体结构。业务领域、SQLite 持久化、
  Xray Adapter、流量采集器和协调器 MUST 保持清晰边界。
- 第一阶段前端 MUST 与 Go 应用同仓库、同进程、同源部署。模板、HTML partial 和
  静态资源 MUST 保持独立目录，但共享一个版本和发布制品。
- 前端依赖 MUST 固定版本并随应用本地提供；不得在生产页面运行时从第三方 CDN 加载
  HTMX、图表库或其他可执行脚本。
- 第一阶段数据库 MUST 使用 SQLite。必须启用 WAL、外键约束和合理的 busy timeout；
  数据库文件 MUST 位于本地持久磁盘，不得位于 NFS 或其他共享文件系统。
- 应用 MUST 以单个写入控制实例运行。后台采集、协调和 HTTP 请求 MUST 共享受控的
  数据库访问策略，避免无界写并发。
- 流量采集 MUST 按节点批量读取，并将一轮结果放入尽可能短的事务。网络 RPC 不得在
  SQLite 写事务持锁期间执行。
- 数据库模式变更 MUST 使用版本化迁移。破坏性迁移前 MUST 生成可验证备份，并提供
  明确的恢复步骤。
- 初始版本不得引入 Redis、消息队列、微服务或 PostgreSQL，除非功能规格提供测量
  证据和复杂度理由。
- 当需要多控制实例、高可用、共享远程数据库或持续高并发写入时，MUST 重新评估并
  形成迁移 PostgreSQL 的独立规格，不得让多个实例直接共享同一个 SQLite 文件。
- 系统 MUST 优雅关闭：停止接收新写请求，完成或取消正在运行的短事务，并保存必要
  的采集游标与待重试状态。

## 开发流程与质量门禁

- 每项功能 MUST 先形成 Spec Kit 规格，包含可验证的验收场景、失败路径、权限边界和
  对配额语义的影响，然后才能进入实现计划。
- 计划和任务 MUST 显式标注数据库迁移、Xray 版本契约、重试/协调行为以及可观测性
  工作；不得把这些内容留作未记录的实现细节。
- 配额计算、周期边界、计数器重置、幂等状态转换和重试退避 MUST 有确定性的单元测试。
- SQLite 事务、迁移和并发访问 MUST 有集成测试；Xray Adapter MUST 针对固定的 Xray
  版本具备契约测试或可重复的端到端测试。
- 模板渲染和 HTML fragment MUST 有 Handler 测试；登录、登出、会话过期、授权和
  CSRF 防护 MUST 有集成测试。
- 创建用户、禁用用户、配额超限和新周期恢复 MUST 至少有一条从浏览器请求到 SQLite
  及 Xray 测试替身的端到端路径。
- 每个影响用户访问权的变更 MUST 覆盖以下故障：数据库提交失败、RPC 超时、RPC 成功
  后进程崩溃、Xray 重启、重复请求和协调器重放。面板管理入站时 MUST 追加覆盖端口冲突
  与端口被面板外进程占用。
- 合并前 MUST 通过格式化、静态检查和完整测试。无法满足宪章的复杂度或例外 MUST 在
  对应规格的 Complexity Tracking 中记录理由、风险、替代方案和移除条件。
- 发布流程 MUST 验证 SQLite 备份与恢复、Xray 连接、启动协调以及禁用用户不会被
  意外恢复。

## Governance

本宪章是 XPanel 工程决策的最高项目规范。规格、计划、任务和实现与本宪章冲突时，
MUST 修改下游文档或先完成宪章修订，不得静默绕过。

- 宪章修订 MUST 记录动机、影响范围、兼容性和迁移计划，并经过维护者明确批准。
- 版本遵循语义化规则：删除原则或不兼容地重定义治理要求为 MAJOR；新增原则或实质
  扩展约束为 MINOR；不改变语义的澄清和文字修正为 PATCH。
- 每次规格和计划评审 MUST 执行 Constitution Check；每次代码评审 MUST 验证相关
  MUST 条款具有实现和测试证据。
- 紧急例外 MUST 有负责人、到期日和修复任务。过期例外 MUST 阻止继续发布。
- 至少在 Xray 版本升级、数据库架构调整、部署拓扑变化、前端交付模式变化或配额
  语义变化时重新审查本宪章。
