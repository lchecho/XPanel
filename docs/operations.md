# XPanel 运维手册：备份、恢复、主密钥与时钟

本文件是 `plan.md §Validation` 与 `contracts/config.md` 引用的运维责任说明，配合发布门禁 `make check` 使用。

## 1. 需要备份的内容

| 项目 | 位置（示例配置） | 说明 |
|---|---|---|
| SQLite 数据库 | `/var/lib/xpanel/xpanel.db` 及 `-wal`/`-shm` | 唯一权威状态：用户、凭证密文、配额、流量聚合、同步意图、审计 |
| 主密钥文件 | `/etc/xpanel/root.key` | 32 字节 Base64，`0600`；**与数据库分开备份、分开存放** |
| 应用配置 | `xpanel.json` | 不含任何密钥或密码，可与数据库一起备份 |

丢失主密钥意味着所有服务端密钥与用户密钥密文不可恢复：需要重新登记入站模板并重建全部用户。
把主密钥与数据库放在同一份备份里会使字段加密失去意义。

## 2. 在线备份

数据库以 WAL 模式运行，可以在服务不停机时做一致性备份。两种等价方式：

```sh
# 方式 A：sqlite3 命令行（推荐）
sqlite3 /var/lib/xpanel/xpanel.db ".backup '/var/backups/xpanel/xpanel-$(date +%F).db'"

# 方式 B：VACUUM INTO（生成紧凑副本）
sqlite3 /var/lib/xpanel/xpanel.db "VACUUM INTO '/var/backups/xpanel/xpanel-$(date +%F).db'"
```

备份文件权限设为 `0600`，目录 `0700`。不要直接复制 `xpanel.db` 文件本身（WAL 未合并会导致副本不一致）；
若必须复制文件，先执行 `PRAGMA wal_checkpoint(TRUNCATE);` 并停止服务。

主密钥单独备份到另一介质或密钥管理系统：

```sh
install -m 0600 /etc/xpanel/root.key /secure/offline/xpanel-root.key
```

## 3. 恢复步骤

1. 停止服务：`systemctl stop xpanel`。
2. 恢复主密钥到 `security.root_key_file` 指定路径，`chmod 0600`，属主为 XPanel 服务账号。
3. 把备份数据库复制到 `storage.database_path`，删除残留的 `-wal`/`-shm` 文件，`chmod 0600`。
4. 启动服务：`systemctl start xpanel`。启动时会：
   - 校验主密钥能解密 `panel_settings.key_verifier`，不匹配则以 `root_key_mismatch` 拒绝就绪；
   - 执行迁移、加锁 `<database>.lock`（单写入实例）；
   - 由协调器把 Xray 实际用户集合收敛到数据库中的期望状态。
5. 验证：
   - `curl -fsS http://127.0.0.1:8080/readyz` 返回 `ready`；
   - 登录后仪表盘节点健康为“健康”，无“持续不同步”标记；
   - 应启用用户在 60 秒内重新出现在 Xray（`GET /users` 状态为“已启用”），手动禁用、配额超限、已删除用户保持不可用；
   - 审计页可见 `reconcile` 相关同步确认。

自动化证据：`tests/integration/backup_restore_test.go` 用 `VACUUM INTO` 备份、在新路径恢复并对模拟重启的 Xray 执行协调，验证上述收敛规则。

## 4. 主密钥丢失或不匹配

- 启动日志出现 `root_key_mismatch`：主密钥文件不是创建数据库时使用的那一份。找回正确的备份后重启。
- 确认无法找回：只能重新初始化数据库（入站模板与用户需重新登记），审计与流量历史可从旧库只读导出保存。
- 第一版不提供主密钥轮换；轮换需要未来的版本化重加密工具。

## 5. 时钟、单实例与日志

- 面板不校验 NTP。启动时若系统时间早于构建时间或数据库中最新的 `updated_at`，会输出警告。请为主机启用 NTP；
  配额周期边界一次计算并以 UTC 存储，时钟回拨不会重开已关闭周期。
- 同一数据库只能由一个 XPanel 进程写入。第二个进程启动会因 `<database>.lock` 被占用而以退出码 3 结束。
- 结构化日志输出到标准错误，由 systemd/journald 或运维日志轮转管理；面板不承诺日志保留期。
  日志已对密码、密钥、令牌与完整 `ss://` URI 脱敏，但仍应按敏感控制面日志保护。
- 审计事件与统计连续性事件不会自动清理；容量规模（≤20 个活跃分配）下增长可控。

## 6. 入站与端口的运维预期

面板为每个用户创建一条专属 Xray 入站并分配独立端口。这些入站只存在于 Xray 的运行时，不写入任何
配置文件，因此有三条运维预期必须知晓。

**Xray 重启会让所有用户短暂不可用。** 重启后全部面板入站消失、端口停止监听，由面板的协调器按数据库
中保存的端口分配整体重建。正常情况下这个窗口是数秒。重启期间面板界面会把受影响用户显示为暂时不可用，
而不是已启用。计划内重启请安排在低峰期。

**端口池需要整段放行。** 端口池在入站模板中配置，面板只在池内分配端口。防火墙必须放行整个区间，
否则新建用户虽然创建成功但外部无法连接。端口池容量即用户数上限；耗尽时面板会拒绝新建并提示扩容位置。

**端口池必须避开其他服务。** 面板不会主动扫描主机端口。若某个端口已被面板外的进程占用，创建入站会
失败，该用户保持「待同步」并在详情页显示可理解的原因；面板会以有界退避持续重试，占用解除后自动收敛。
不想等的话，在用户详情页点「更换端口」，选一个端口池内的空闲端口即可——面板会先移除旧入站再按新端口
重建，该用户在这期间短暂不可用，且必须把新的连接信息重新交付给使用者（旧链接的端口已经变了）。缩小端口池不会影响已经分配在池外的既有用户，模板详情页会把这些端口
标识出来，并注明它们不计入「已分配」。

**面板只碰自己命名空间内的入站。** 面板创建的入站标签一律以 `xpanel-` 开头，面板拒绝对其它标签执行
任何变更；运维在配置文件中自建的入站在全流程中保持不动，也不计入面板统计。反过来，命名空间内出现
面板没有记录的入站会被当作漂移清理并释放端口，因此**不要手工创建以 `xpanel-` 开头的入站**。

### 6.1 端口池扩容流程

端口池容量即用户数上限。仪表盘的「端口池」区块显示池容量、已分配与剩余可分配；剩余为 0 时新建会被
拒绝并提示扩容位置。扩容步骤：

1. 选定新的端口区间，确认区间内没有其它服务在监听（例如 `ss -ltn` 或 `lsof -iTCP -sTCP:LISTEN`）。
2. 在防火墙／安全组中整段放行新区间，先放行再改面板，避免出现「创建成功但外部连不上」。
3. 打开「入站模板 → 编辑」，把端口池起止改为新区间并保存。保存只影响此后的分配，既有用户不受影响。
4. 回到模板详情页核对「端口池」一行的容量与剩余数；若之前缩小过端口池，页面会列出落在池外的既有端口。

缩小端口池同样即时生效且不中断既有用户：落在新区间之外的分配继续可用，只是不再计入「已分配」，
并在模板详情页单独列出。要真正回收这些端口，只能删除对应用户。

## 7. 迁移 00004 的破坏性说明

迁移 `00004_per_user_inbound.sql` 把访问配置改造为入站模板、新建专属入站表并清理 bootstrap 身份，
属于破坏性变更：它会删除全部访问模型数据（模板、身份、分配、凭证、配额、流量、同步意图），
只保留管理员、会话、面板设置、实例与审计记录。原因是 001 的共享入站模型下的用户在新模型中无法运行
（没有端口、没有专属入站）。

执行前 MUST 按第 2 节生成可验证备份，并按第 3 节实际演练一次恢复。建议顺序：

1. 停止面板进程（确认 `<database>.lock` 已释放）。
2. 生成备份并**在另一个目录恢复一次**，用 `PRAGMA integrity_check` 与 `PRAGMA foreign_key_check` 验证。
3. 启动新版本面板，迁移在启动时自动执行。
4. 登记入站模板（监听地址 + 端口池），逐个重建用户并把新的连接信息交付给使用者——
   旧的 `ss://` 链接在新模型下一律失效，因为端口与服务端密钥都变了。

该迁移提供了 `-- +goose Down`，回滚只恢复 001 的表结构，不恢复任何数据。回滚后需要重新登记访问配置（001 概念）
并重建用户。（Down 内部必须先把 `inbound_templates` 改名回 `access_profiles`，SQLite 才会把其它表指向
它的外键引用一并改回；顺序颠倒会留下悬空外键，使迁移无法再次执行。`migrations_test.go` 覆盖了
up → down → up 往返。）
